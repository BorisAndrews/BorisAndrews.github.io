# CLAUDE.md — borisandrews.github.io

Jekyll academic portfolio. Theme: `jekyll-theme-minimal` (heavily customised).

## Build

**Build and check locally with `Software/site-check`** (from the workspace root, or by absolute path):

```sh
Software/site-check            # build out of tree, report Jekyll errors, broken internal links and missing `#anchor` targets
Software/site-check --serve    # live preview at http://localhost:4000
```

Run it after any edit here. It catches what inspection can't — Liquid errors, missing includes, and links to pages that no longer build (it ignores links inside HTML comments). Output goes to `~/Library/Caches/claude-site/_site`, never to `_site/` in the repo.

The deployed site is built by GitHub Pages on push to `main`, so **a push here publishes the public site**. Like every commit and push in this workspace, it needs Boris's explicit permission for that specific commit or push (root CLAUDE.md).

How the local build is set up (Oct 2026), and the traps found doing it:

- The `Gemfile` pins `github-pages` **= 232**, the version on `https://pages.github.com/versions.json` (Jekyll 3.10.0, jekyll-seo-tag 2.8.0, kramdown 2.4.0, Liquid 4.0.4). Re-check that file and bump the pin if Pages moves.
- It **must run on Ruby 3.3** (Homebrew `ruby@3.3`, keg-only at `/opt/homebrew/opt/ruby@3.3/bin`), matching Pages' Ruby 3.3. Homebrew's default `ruby` is 4.0, where `github-pages` 232 cannot install (`commonmarker` 0.23 requires Ruby < 4.0); Bundler then silently resolves an old `github-pages` 223 that crashes on `require 'csv'`. macOS's `/usr/bin/ruby` (2.6) is too old. `site-check` calls ruby@3.3 by path, so PATH doesn't matter.
- Gems live in `vendor/bundle` (via the repo-local `.bundle/config`); both gitignored.
- **Jekyll 3 replaces its default `exclude` list** when `_config.yml` sets one (the comment in `_config.yml` describes Jekyll 4's behaviour, not this). So `Gemfile`, `Gemfile.lock`, `vendor/` and `.bundle/` are listed there explicitly; without them the build tries to render the gems' own templates and fails, and the Gemfile would be published as a static file.
- `To use retry middleware with Faraday v2.0+...` and `GitHub Metadata: No GitHub API authentication...` are harmless; `site-check` filters them.

The one other locally buildable thing is the PDF CV — see `cv/assets/pdf/CLAUDE.md`.

No Makefile. Edit source files directly. The main stylesheet is `_sass/jekyll-theme-minimal.scss`, compiled by the theme into `/assets/css/style.css` at build time (that file is not in the repo). The files that *are* in `assets/css/` (`highlight-box`, `reveal-box`, `gallery`, `timeline`, `video-container`) are hand-written component stylesheets, each loaded by its `_includes/<name>.md`; edit them directly.

## Style conventions

**Look and feel decisions (Nov 2026).** A trial restyle swapped the body text to a serif (Source Serif 4) and the diagonal-stripe gradients for flat colours; Boris rejected both firmly ("horrendous"). **Keep JetBrains Mono throughout and keep the stripes** (nav buttons, `highlight-box`, `reveal-box`). What he kept: publication lists as cards (`table.pubs` in `_sass/jekyll-theme-minimal.scss`, switched on by a `{: .pubs}` line, or `{: .pubs .pubs-thin}` for the two-column draft lists, at the end of each `_includes/publications/lists/*.md`), and a wider fluid content column (`section` up to 720px, `.wrapper` up to 1060px). The card rows still come from the same `all/<slug>.md` table rows, so adding a paper is unchanged. In those rows **each co-author is wrapped in `<span class="au">…</span>`, with nothing between them** (`<span class="au">{% include collaborators/matin/short.md %}</span><span class="au">{% include collaborators/patrick/short.md %}</span>`), and the CSS draws Boris's light `|` dividers between them. It is the same divider style as the paper-page bylines: a wrapped line ends with `|` and never starts with one (Nov 2026). The divider is pale tan on light bands and dark tan on dark ones (`--divider`). Until then they were ` <code>&#124;</code> <br> ` separators, which could leave a `|` dangling at a line end. Sub-groups within a list (Upcoming, In review, Drafts available on request …) are a plain line with `{: .pubs-group}` straight under it, rendered as a small brown capitals label (Nov 2026, the same on the homepage, CV and publications page). They replaced italic `*(Upcoming)*` paragraphs and `### (Upcoming)` headings, which Boris found ugly. Rows in `4-review` carry no "In review" in their date cell: the IN REVIEW group label says it once for the list (Boris, Nov 2026: "no need to say it 5 times"). The date cell has **no commas** (Nov 2026): `MON.YYYY <br> ([arXiv](…)) <br> MON.YYYY <br> ([JOURNAL](…))`. The card CSS hides every other `<br>` in it, so each date shares a line with its venue (`NOV.2025 (arXiv)` / `APR.2026 (SISC)`), at the same 14px as the titles in a 10.5em column.

**Space after tables** (Nov 2026): `table` has a 36px bottom margin, against 20px for paragraphs and lists, because a heading straight after a card list or schedule looked cramped (Boris). The same 36px applies after the CV page's entry lists (`.cv > ul`) and between a collaborator card and a following heading, which also end in a rule. All of it is set right after the shared `p, ul, ol, table, pre, dl` rule in the scss.

**Homepage "Recent collaborators" gallery** is hand-written HTML in `index.md` (not includes), a carousel since Nov 2026: two rows of square photos with `grid-auto-flow: column`, so items fill *column by column* (1st top-left, 2nd below it, 3rd top of column 2). Four columns are in view, or two below 600px, and the track scrolls sideways with scroll-snap. The striped ‹ › buttons under it (`assets/js/gallery.js`) pan one screenful and disable themselves at each end; on phones it also swipes. It lists everyone on `collaborators/index.md` who has a real photo, in that page's order (all 18 as of Nov 2026). Someone new who is still on `placeholder.svg` stays off the carousel until their photo arrives, so adding a photo means adding a gallery item too. Captions are name, `<br>`, affiliation, with no comma. Each photo is wrapped in a link to the same site as the caption's name (`tabindex="-1"`), except Matin's. `ganghui.jpg` had a saturated studio-blue background (RGB 31,185,255) that clashed with the palette; it was recoloured to a muted version of the same blue, `#72AECA` (Nov 2026; the original is in git history). A far-off colour (a beige was tried first) leaves a visible blue fringe in the fine hair, because the original JPEG's hair edges are themselves blue-tinted; keep the replacement near the original hue and just drop the saturation. Method, for any future photo with a flat garish backdrop: opacity `a = clip((|pixel - bg| - 18) / 92, 0, 1)` per pixel, then `pixel + (1 - a)·(new - bg)`, which swaps only the backdrop's share of each pixel, so hair edges get no halo (numpy + PIL).

**Sliding stripes on hover** (Nov 2026, Boris's long-standing wish): nav buttons, `highlight-box`, `reveal-box` and the gallery arrows draw their stripes on a `::before` layer, not on the element's own background. The layer is 30px wider on the left, sits at `z-index: -1` inside an `isolation: isolate; overflow: hidden` parent, and on hover runs `translateX(28.2843px)` in a loop, one period per 1.6s (it was 1s; Boris asked for it slightly less pronounced). That distance is one stripe period: 20px across 135° stripes is 20√2 px horizontally, so the loop has no seam. Change the stripe widths and that number must change with them. The animation is `paused` until hover (`animation-play-state`), so it resumes rather than snapping back, and is off under `prefers-reduced-motion`. Hovering also grows each button by a 1px rim (`box-shadow: 0 0 0 1px` in the darker hover stripe colour, eased over 0.15s; 2px was too pronounced). It is a ring rather than `transform: scale`, so a tall open reveal-box grows by the same amount as a small nav button. The hovered element also gets `background-color` in that same colour underneath the stripe layer; without it the stripe layer's anti-aliased rounded corners let a beige hairline show inside the ring. Animating `background-position` instead would need a tile size of 28.28px, which leaves sub-pixel seams.

**Every page is laid out as alternating light and dark bands** (Boris, Nov 2026: he found the homepage sections hard to tell apart, liked the bands there, and asked for them on every page). Both `_layouts/default.html` and `_layouts/blank.html` pass the rendered page through `_includes/bands.html`, which cuts it at every `<h2` and wraps each piece in `<div class="band band-light|band-dark">`, alternating, starting light. Its header comment documents the rules, and the ones that matter when editing pages are these:
- **A cut inside an unclosed `<div>` or `<details>` is skipped.** h2s inside collaborator cards (`## {% include …/full.md %}`) or inside a reading-group `<summary>` therefore don't cut. Where a page wants a cut that has no top-level h2, it says `<!-- band -->`. `collaborators/index.md` has one before every card (keep it when re-sorting), and `reading-group/index.md` has one before the PAST `<details>`.
- **`{: .band-keep}` under an h2 keeps it in the band before** (the FETC page's subtitle).
- **A short opening joins the first section.** The pre-h2 opening becomes a band of its own only if it has 200+ characters of text (the homepage, paper pages, the reading group). A bare title (Publications, Notebooks, CV, Collaborators) joins the first section instead, because Boris found a thin light strip followed by a dark first section odd: the first *full* section must be light.
- `<p><br /></p>` spacers are stripped, since the bands separate the sections. `layout: blank` pages run their bands across the whole window, text included, and start **dark** (`start="dark"` in `_layouts/blank.html`; preview for Boris, 4 Nov 2026), with the "Back to home" link on a cream strip above the first band (outside the bands) and the page title in a lighter brown (`.band-dark h1`, `#E0875C`) so it reads on the dark ground (Boris).
- A page can add a class to every band with `band_class:` in its front matter. The CV uses `band_class: cv`, which is how the `.cv` rules (`.cv > ul > li` …) still apply now that the page has no single `<div class="cv">` wrapper (one div round every section would have stopped every cut). Because the band *is* the `.cv` element there, every `.band-dark .cv …` override needs a twin `.band-dark.cv …` (`&.cv` in the scss); missing that left the CV's dark sections with light-grey rules. The collaborators page uses `band-compact` for thinner bands (Boris wanted the cards closer).
- The dark colours, and every component's dark variant (rules, `code`, `th`, timeline dot ring, reveal-box hover, reading-group summaries), are under `.band-dark` near the end of the scss. A new component that may land in a dark band needs its text and rule colours added there.
- Boris wanted square-edged, full-width stripes, not rounded cards.

**Page frame** (Nov 2026, sitewide, part of the same change): the sidebar `header` is a full-height panel in sand (`$side-ground`, `#E9DDBF`), a colour between the light and dark bands. `.wrapper` is a two-column grid (370px panel, then a content column of at most 820px), no longer the theme's centred 1060px float layout. The wrapper's background is the same sand, so any width left over on the right is sand too, and only the content column (`section`, with a cream background) carries the stripes. That `max()` has to go through `unquote("…")`, because the old Sass in github-pages treats a bare `max()` as its own function and fails ("50px is not a number for `max'"). ## Adding content

**New publication page**: create `publications/<slug>/index.md` following the pattern above; add entry to `_includes/publications/` list file for appropriate status.

**New collaborator**: add `_includes/collaborators/<name>/short.md` and `full.md`; optionally add photo to `assets/img/collaborators/`.

**New standalone page**: `<slug>/index.md` with front matter of just `title` and `permalink: /<slug>/` — **do not** add a `layout:` key. Jekyll applies `default` (sidebar, nav, maths) on its own, which is what most pages want; the reading-group pages and `fetc-workshop/` opt into `layout: blank` deliberately (and so get no maths rendering). A new page is *not* automatically reachable: the sidebar nav is hardcoded in `_layouts/default.html`, so either add an `<li>` there or link the page from wherever it belongs (`fetc-workshop/` is reached from the `UPCOMING` list in `index.md`, the way paper pages are reached from the publication lists — its `conferences/2027/fetc.md` include *is* the link).

**New conference**: add `_includes/conferences/<year>/<name>.md` (one line: the linked event name, or plain text if it has no site yet) and include it wherever it is referenced — the `UPCOMING` list in `index.md`, the TALKS lines in `cv/index.md`, or a publication page.

**New person**: `_includes/collaborators/<firstname>/short.md`, one line, `[Full Name](link)`. When two people share a first name, both switch to `<firstname>_<surname>` (lower case, surname hyphens kept), matching the photo filenames — `aaron_brunk/` and `aaron_baier-reinio/`, with `assets/img/collaborators/aaron_brunk.jpeg` and `aaron_baier-reinio.jpg`. Renaming an existing directory means grepping for every `collaborators/<old>/` include: they are spread across publication rows, minisymposia, the collaborators page and each person's own `full.md`. (The publication slug `aaron-brunk.md` was deliberately *not* renamed; slugs don't track coauthors.) `full.md`, a photo under `assets/img/collaborators/` and an entry on `collaborators/index.md` are only for genuine research collaborators — people who appear merely as organisers or co-hosts (the Oberwolfach organisers, the FETC workshop co-organisers) get `short.md` alone.

**Publication row files (`_includes/publications/all/*.md`) must not end with a newline.** They are included one per line into the list files, so a trailing newline becomes a blank line inside the Markdown table, which ends the table: every row after it is rendered as a second, headerless table with its own column widths (seen Oct 2026, `irksome-galerkin.md`, which made the last In-review row's co-authors jump sideways). Write them with `printf`/`write_text` without a final `\n`; `Software/site-check` reports any headerless table.

**Revised arXiv preprint** (a new vN of a paper already on the site) touches four places, and it is easy to stop after the first:

1. `_includes/publications/all/<slug>.md` — the date in the table row.
2. `_includes/publications/lists/4-review.md` — the lists are hand-ordered **newest first**, so a bumped date usually means moving the line.
3. `publications/<slug>/index.md` — the date heading, *and both copies of the abstract*: the bolded pull-quote `> blockquote` and the full text inside the FULL ABSTRACT reveal-box. Check the surrounding prose too; it paraphrases the abstract, so a changed term needs changing there as well.
4. `cv/assets/pdf/components/papers.tex` — the `\cventry` date, likely also reordered. Rebuild `cv.pdf`.

The DOI link (`10.48550/arXiv.NNNN.NNNNN`) is versionless and never changes.

Get the abstract and dates from the **API**, not the abs page — `https://export.arxiv.org/api/query?id_list=<id>` returns `<published>` (v1), `<updated>` (current version) and a verbatim `<summary>`, with no risk of a paraphrase creeping into a quoted abstract. Note plain `http://` returns an empty body; use `https` and `-L`.

Two ways the API fails, both silently: a paper posted in the last day or so can be **missing from the feed entirely** (a valid Atom response with no `<entry>`), and repeated calls get a plain-text `Rate exceeded.` instead of XML. WebFetch on the abs page is no substitute for a quoted abstract — it summarises. The verbatim fallback is `curl -sL -A "Mozilla/5.0" https://arxiv.org/abs/<id>` and taking the text of `<blockquote class="abstract ...">` (strip the `Abstract:` descriptor span); the submission history is on the same page.

**The arXiv date is always the date of the most recent version**, never v1 — Boris settled this in Aug 2026, and all rows were brought into line then (`parker` JAN.2025→NOV.2025, `sp-integrators-a` APR.2025→SEP.2025, `sp-integrators-b` NOV.2025→AUG.2026). It applies to published papers too, where the arXiv date sits beside a separate journal date; only the arXiv half moves. Take it from the API's `<updated>`, not `<published>`.

**Never name the journal for a paper that is only in review.** Boris's policy since Sep 2026, in case of rejection: an in-review row reads just `In&nbsp;review`, its page heading just `In review`, and its PDF `\cventry` has no item block. The journal is added at acceptance (recipe below) and not before. Where a paper was sent is still recorded privately in the `Papers/` CLAUDE.md files — that's fine, they aren't published.

**Paper submitted, arXiv not out yet.** Precedent: `geometric-flows` (May 2026) and `enstrophy` (Sep 2026).

- The row moves from a **2-column** list (`6-drafts`/`7-future`, `titles/thin.md`: title | coauthors) to the **3-column** `4-review` (`titles/wide.md`: date | title | coauthors), so the row must gain a date cell — moving the include line alone breaks the table.
- Date cell: `MON.YYYY <br> (arXiv) <br> In&nbsp;review` — **no journal** (see the policy below) — "(arXiv)" as **unlinked** placeholder text until the DOI exists. The month is the expected arXiv month, which is normally the submission month.
- Title becomes a link to `/publications/<slug>/`; remove the `*` (= "in preparation") after the title in coauthors' `collaborators/*/full.md` and link it there too.
- Paper page: date/venue heading, pull-quote and full abstract (from the submitted `.tex`, converting `--` to `–` and dropping `~`). **Omit** the CHECK OUT ON ARXIV highlight-box until there is something to link to.
- PDF CV: add a `\cventry` at the top of `(In review)` with a plain (un-`\href`'d) title.
- **Banner:** a banner needs a destination, so for `enstrophy` Boris waited for the arXiv DOI. For Stefan–Maxwell (26 Oct 2026) he wanted it straight away, so the paper got its own page (title, authors, `In review` heading, abstract, no arXiv box) and the banner points there. Ask which he wants.
- Once the DOI arrives: link "(arXiv)" in the row and page heading, add the arXiv highlight-box(es) to the page, `\href` the CV title, and then the banner.

**Paper accepted** (no DOI yet). Follow the precedent set by `parker` (Nov 2025) and `sp-integrators-b` (Sep 2026):

1. `_includes/publications/all/<slug>.md` — `In&nbsp;review` → `Upcoming <br> ({% include journals/<j>.md %})`. This is the first point at which the journal appears.
2. Move the include line from `lists/4-review.md` to `lists/3-accepted.md`.
3. Uncomment the "Accepted for publication" heading *and* its `3-accepted.md` include in **three** pages — `index.md`, `cv/index.md`, `publications/index.md`. They are kept commented out while the list is empty, so an accepted paper is otherwise silently invisible. Re-comment them when the list empties again.
4. `publications/<slug>/index.md` date heading — `In review` → `Upcoming ({% include journals/<j>.md %})`.
5. `cv/assets/pdf/components/papers.tex` — uncomment the `(Accepted for publication)` subsection, move the `\cventry` under it, and give it an item block `\begin{itemize} \item Accepted: \emph{<Journal name> (<ABBR>)} \end{itemize}` (in-review entries have an empty last argument, `{}`). Rebuild with `Software/latex-check`.
6. Homepage `highlight-box` banner — house wording is `MY WORK WITH … ON … WAS RECENTLY ACCEPTED AT <JOURNAL>`, linking to the paper page.
7. Grep for prose elsewhere calling it "submitted" (e.g. `sp-integrators-a` cross-links to `-b`).

**Once published** — this happens in **two stages**, and Boris uses both (`sp-integrators-b`, Sep 2026):

**Stage 1, DOI but no volume/issue/pages** (Elsevier "article in press"; Crossref carries only a month). The paper belongs in `2-upcoming`, *not* `1-papers`, with the `(Upcoming)` heading and include uncommented in all three pages, and its `\cventry` under the `(Upcoming)` subsection in `papers.tex` (kept commented out while empty, like the accepted one). **Stage 2, once the issue is assigned** — and **the issue date has arrived**. A paper whose volume and pages are known but whose issue is dated in the future stays in `2-upcoming`, with the issue month in its row and the volume/pages already on the CV: `sp-integrators-b` is 224, pp. 1–23, dated 15 Dec 2026, so it shows `DEC.2026` under Upcoming until then (Boris, Oct 2026). Then: move to `1-papers` and the `\subsection{Papers}` block, and add `, <vol> (<issue>), pp.~<range>` to the CV item as the SISC entries do.

Either way: replace `Upcoming (<journal include>)` with `MON.YYYY ([<JOURNAL>](https://doi.org/…))` as in `parker.md`, and move to `1-papers.md`, re-commenting the now-empty accepted sections in all three pages. In the PDF CV the `\cventry` moves up into `\subsection{Papers}` and its item becomes `Publication:`. Note Crossref may carry only a month for a new Elsevier DOI — no volume/issue/pages — so cite the journal name alone until they appear. History shows an intermediate `2-upcoming` stage ("Papers (Upcoming)") was used when a DOI existed but the issue date didn't; it's optional.

**Reading group page.** Since Nov 2026 it is all one page, `reading-group/index.md`. Everything sits under UPCOMING (schedule), with three collapsible `<details class="rg-toggle">` sections: REFERENCES (`#references`), PAST (`#past`), and inside PAST its own REFERENCES (`#past-references`). It used to be four near-identical pages, one for each combination of open sections. The summary line keeps the old look, a link-coloured heading and "Click to view/hide …". `assets/js/reading-group.js` opens every enclosing section when an anchor link, or a page load with a hash, targets something inside one; browsers don't reliably do this themselves. It also keeps the address bar in step with what is open. The old URLs (`/reading-group/past/`, `/references/`, `/past/references/`, plus any `#id` on them) forward to the right section through `layout: forward` stubs. The upcoming REFERENCES section shows **only when `upcoming/references.md` contains an entry** (a Liquid `contains "{: #"` test), so it no longer needs commenting in and out each term.

**Reading group references.** A talk's references go in `_includes/reading-group/upcoming/references.md` (grouped by `***<year>***` then `*<term> term*`), one list item each with an id, and the schedule row cites them as `Topic ([Author, Year](/reading-group/#<id>))`. Ids are `<surnames>-<year>` (`briggs-henson-mccormick-2000`, or `<first>-et-al-<year>`) and **must be unique across the upcoming and past lists**, which now share one page. When a term ends, its rows and references move to `past/schedule.md` and `past/references.md` and **the links need no change**: since the merge every reference is `/reading-group/#id`. (Before that, four links were once missed when they had to be repointed to `/reading-group/past/references/`.) One silent trap remains: **write the id as `- {: #id} **A. Author**, ...`, i.e. right after the bullet.** The older entries put `{: #id}` on an indented line *after* the text. That only works because kramdown wraps the items of a *loose* list (blank line between entries) in `<p>` and attaches the id to that. A list with one entry is never loose, so a lone entry silently loses its id. A missing `#` (`{: some-id}`) also fails silently. `Software/site-check` checks every `#anchor`, so run it after any of this.

**Reading group mailing list** (`fem-reading-group@maths.ox.ac.uk`, Mailman 2.1, set up Oct 2026). The subscribe link in `_includes/reading-group/intro.md` is a `mailto:` to `fem-reading-group-join@maths.ox.ac.uk`, not the listinfo page, because the department's site-wide listinfo template has the web subscribe form removed: that page only offers unsubscribing and an admin login. The list's message footer (reading group link and unsubscribe address) arrives in Outlook as an attachment, `ATT00001.txt`, because Mailman 2 can't add text inside an HTML email. Boris knows and has chosen to keep it (Oct 2026); don't remove it or switch the list to plain text to "fix" this. The admin note in `_includes/reading-group/intro.md` is a Liquid `{% comment %}` rather than an HTML comment, since kramdown copies HTML comments into the built page.

**Reading group organisers** (run jointly with Tom Higham, `collaborators/tom/`, since Sep 2026) are named in four places that must change together: the homepage section in `index.md`, `_includes/reading-group/intro.md` (shown on `/reading-group/`, which uses `layout: blank` with no sidebar, so Boris is named and linked there explicitly), `_includes/experience/reading_group.md` (web CV) and `cv/assets/pdf/components/experience.tex`.

**New organised event**: an event Boris co-organises goes in three places — the `UPCOMING` list in `index.md`, `_includes/minisymposia/<name>.md` for the CV page's HOSTED WORKSHOPS & MINISYMPOSIA section, and a matching `\cventry` in `cv/assets/pdf/components/minisymposia.tex` (the PDF CV duplicates the content in raw LaTeX with hardcoded `\href`s — it shares no includes with the site, so it must be edited by hand and rebuilt).

## Link previews and sitemap (Nov 2026)

- `_config.yml` sets `url: https://borisandrews.github.io` explicitly, so `og:image`, `og:url`, canonical links and sitemap entries are absolute in every build (the out-of-tree `site-check` build otherwise left them relative). Under `--serve` Jekyll swaps in localhost, as it should.
- `jekyll-seo-tag` (`{% seo %}`) writes the preview tags from each page's front matter: `title`, `description`, `image`. The site-wide `description` in `_config.yml` is the sidebar tagline, so every page that matters sets its own `description` rather than inheriting it. A `defaults` block gives every page the portrait as `image` with `twitter: card: summary` (small square card). `parker` (corona) and `sp-integrators-b` (engine plot) override it with a figure and `summary_large_image`; pages with only videos, or with no figure, keep the portrait.
- `index.md` deliberately has **no `title`**: seo-tag then titles the homepage "BORIS ANDREWS | <tagline>" with og:title "BORIS ANDREWS", rather than "HOME".
- `_layouts/blank.html` keeps its own `<title>` and calls `{% seo title=false %}`, so the reading group and FETC pages get preview tags too.
- The sitemap is generated by `jekyll-sitemap` (on GitHub Pages' plugin whitelist) and lists every built page and PDF. Anything unlinked or private carries `sitemap: false`: `notebooks/`, `publications/bvps/` and `ap-integrators/` (their list rows are commented out), `reading-group/suggested/`, and the three `layout: forward` stubs. `_config.yml` defaults exclude the Search Console file and the speakers' slides under `assets/pdf/reading-group/`. A new page that shouldn't be found by search needs `sitemap: false`.

## Sticky sidebar (Nov 2026)

On desktop (above 960px) the sidebar stays in view while the page scrolls, **but only when all of it fits in the window** (Boris: the nav buttons must never poke out of the bottom). `assets/js/sidebar.js` sets `header.sticky` when the distance from the top of the sidebar to the bottom of its `nav`, plus 16px, is at most `innerHeight`, rechecking on resize and load. It measures to the nav, not `offsetHeight`, because the header's 50px bottom padding is only sand: the first version counted it and refused to stick in windows where every button was visible. The scss makes `header` `align-self:start` (so it is only as tall as its contents and has room to move) and `header.sticky` `position:sticky; top:0`. The buttons end about 766px down, so it sticks in windows at least ~785px tall. Adding a nav item raises that threshold.

The local-only "View the Project on GitHub" line has been **deleted from `_layouts/default.html`** (it rendered only in local previews, and made the local sidebar taller than the live one, which changed where it starts sticking). Don't try hiding it with `header p.view`: the email and Oxford-profile lines are `p.view` too, and a first attempt hid them all.

## Sidebar details (Nov 2026)

- **Current page**: each nav link gets `aria-current="page"` when the first segment of `page.url` matches it (Liquid at the top of the `<nav>` in `_layouts/default.html`; `''` for the homepage). Paper pages therefore light up PUBLICATIONS. The scss gives `[aria-current="page"]` the darker hover stripes at rest.
- **Portrait**: wrapped in `<a class="portrait" href="/" tabindex="-1">`, so clicking it goes home like the name does (Boris; `tabindex=-1` because the name is already that link for keyboard users). Corners rounded to 8px, like the buttons and the gallery photos (Boris). The img must stay inline on desktop: `display:block` once removed the few pixels below it and moved the tagline up.
- **Narrow screens** (960px and below, where the sidebar sits above the content): the header is a grid, with the portrait small on the left (150px, 96px below 480px) beside the name and tagline, then the email, icons and Oxford-profile link at full width, then the nav as a two-column grid of buttons, with HOME spanning both when the count is odd (Boris preferred that to READING GROUP spanning). Before, a phone's whole first screen was the name, a full-width portrait and five stacked buttons (Boris asked for a better opening screen); now the page itself starts about halfway down the first screen. The theme's old `padding-right:320px` on the narrow header is gone.

## Mesh bands (Nov 2026, trial)

Every third band (`band-mesh`, added by `_includes/bands.html` when `(n+1) mod 3 == 0`) has a faint triangular-mesh background, Boris's idea for a "more interesting, mesh-inspired" background that stays still while the page scrolls (`background-attachment: fixed`; iOS Safari ignores `fixed` and scrolls it with the page). Since the bands alternate, the mesh bands alternate light and dark, so there are two tiles: `assets/img/mesh-light.svg` (lines `#F5EEDB`, vertices `#F1E8D1` on the cream) and `mesh-dark.svg` (`#2B3033` / `#2E3437` on `#252A2C`); Boris found the first, stronger pair (`#EEE4C9` / `#30373A`) too contrasty. Each is a seamless 960 x 880 tile, a triangular lattice (edge 64px, rows 55px, whole pixels so the tile has no seam) with each vertex perturbed periodically, so the repeat is invisible at the edges. Among the warm mesh lines the theme's neutral `#e5e5e5` rules looked blue to Boris (and then, once he had noticed, in plain bands too), so every light-ground rule on the site is now the warm grey `$light-rule` (`#E4DDCD`), set at the top of the scss. Use that variable for any new rule on a light band, never a neutral grey. They were generated by a short Python script (not kept in the repo): change the colours or density by regenerating rather than hand-editing the 38KB of path data.

## Adding CLAUDE.md files

Any new CLAUDE.md created inside this directory must be added to the `exclude` list in `_config.yml`. Jekyll processes all `.md` files it finds, and Liquid syntax in CLAUDE.md files will break the build. The current excludes are `CLAUDE.md`, `assets/ipynb/CLAUDE.md`, `cv/CLAUDE.md`, and `cv/assets/pdf/CLAUDE.md`.
